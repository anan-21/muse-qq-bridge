# 延迟拆分与测速

## 流程与时间边界

QQ 入站经过腾讯网关、适配器和小桥入队，收件钩子发现 pending 后取正文并唤醒 Muse。智能体准备好回复后，回复 helper 发送，再确认本批消息。

| 时间点 | 证据来源 | 含义 |
| --- | --- | --- |
| 钩子开始 | 钩子执行记录 | 本次检查开始，消息可能已经在队列中等待 |
| 返回 wake | 钩子执行记录 | 检查和取件完成，输出唤醒数据 |
| 请求创建 | Muse 运行时记录 | 回合请求创建，包含后续调度等待的起点 |
| `helper_start` | 私有计时日志 | 回复脚本入口时间 |
| `send_done` | 私有计时日志 | 发送接口返回结果，仍需检查是否成功 |
| `ack_done` | 私有计时日志 | 确认接口返回结果，仅在确实调用时记录 |

用同一消息 ID 对齐这些时间。多条消息合并回复时，对齐本次 helper 的 ID 列表。跨进程记录采用 UTC 毫秒时间戳，先核对机器时钟；同一进程的区间可另用单调时钟量取。

请求创建到 helper 启动之间可能含调度、上下文装配、模型处理和工具等待。只有找到对应的工具起止记录，才继续细分。文件修改时间无法代替脚本调用时间，稀疏的 pending 采样也只能给出清零窗口。

把取件前移进钩子后，应比较“钩子开始到发送/确认完成”。单看 wake 之后的变化，会漏掉前移的 HTTP 取件耗时。完整的用户等待还包含发出消息到钩子发现消息，以及腾讯回执后手机显示消息的区间。

## 2026-11-07 现场样本

以下是已有运行环境中两次同类短回复的对照。该环境同时精简了重复运维说明，并启用入站自动带正文；公开仓库保留经过通用化的代码和测试。

| 可观测阶段 | 改动前 | 改动后 |
| --- | ---: | ---: |
| 钩子开始到 wake | 1.615 秒 | 1.745 秒 |
| wake 到请求创建 | 0.066 秒 | 0.291 秒 |
| 请求创建到 helper 启动 | 19.609 秒 | 3.616 秒 |
| helper 启动到发送返回 | 1.154 秒 | 2.342 秒 |
| 发送返回到确认返回 | 0.635 秒 | 1.120 秒 |
| 钩子开始到发送返回 | 22.444 秒 | 7.994 秒 |
| 钩子开始到确认返回 | **23.079 秒** | **9.114 秒** |

这一组样本缩短 13.965 秒，约 60.5%。改动后唤醒数据带有同一条消息的 `id/from/text/time`，上下文条目只观察到一次与 helper 启动对齐的 `exec`，未观察到单独补取正文的工具回合。字段级命令原文没有留下可核查记录。

这是一组单样本比较。模型状态、工具轮数和上下文都有变化，缓存计数与输入分类缺失，因此无法分别归因记忆精简和取件前移的贡献，也无法给出稳定时延保证。使用者确认收到回复，手机实际显示时刻没有记录。

## 测自己的环境

1. 选择同类、同长度的简单消息，记录发送时刻及并发任务情况。
2. 对齐同批 ID 的钩子、运行时与 helper 记录，保留原始时间和各段差值。
3. 核对 wake 数据有完整字段，并查看是否仍有额外 `/inbox` 工具回合。
4. 记录 `/send` 与 `/ack` 的实际结果。发送成功和队列确认是两个阶段。
5. 多次同条件测量后比较中位数与范围。只有一个样本时，报告该样本的差异。

计时日志保存在部署者本地，采用私有权限。公开问题报告只提供脱敏阶段、时间、结果和版本，避免上传消息正文、身份、凭据或生产日志。
