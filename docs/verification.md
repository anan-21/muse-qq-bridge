# 验收范围

## 原始部署

2026-10-29，使用者确认官方 QQ 路线端到端通过：QQ 发问题 → 官方适配器 → 小桥 pending 增加 → Muse 中的原智能体回复 → QQ 本人收到。使用者随后报告，原智能体已开启每分钟检查桥的常驻任务。

独立观察到的部署证据包括：官方沙箱 gateway_ready、持久化主人绑定、仅 loopback 的适配器监听、已签名转发、私网 health pending 从 0 到 1。该次服务器在隔离队列与 dummy key 下通过 17 项适配器自测。最终收到回复及一分钟任务常驻的确认来自使用者；没有把它们写成独立监视器的长期稳定性证明。

实际部署环境：Ubuntu 24.04 / Python 3.12.3 / amd64；官方 SDK `qq-botpy 1.2.1`，HTTP 依赖 `aiohttp 3.14.5`。不发布实际账号、应用 ID、域名、IP、消息 ID、密钥或运行数据库。

## 2026-11-07 入站自动带正文

已有运行环境中，Muse 工具环境与部署者电脑分别通过私网取得 `/inbox-tailnet` 的 HTTP 200。Muse 侧收件脚本在原本应唤醒时取正文，成功则把本批 `id/from/text/time` 放入唤醒数据；失败时沿用 pending-only 唤醒，由原智能体补取。

现场版本经过 `bash -n` 和隔离状态、本地替身的 6 项检查，覆盖 pending 为 0、正文齐全、取件 HTTP 500、消息缺字段、空消息数组，以及冷却去重和清零重置。这些检查没有发送真实 QQ 消息。

随后使用者发送同类短消息，并确认收到回复。该轮唤醒数据包含一条字段齐全的消息，ID 与计时日志一致。上下文条目仅观察到一次与回复 helper 启动对齐的 `exec`，未观察到独立补取正文的工具回合；命令字段原文缺失。

同类样本的“钩子开始到确认完成”从 23.079 秒变为 9.114 秒。详细分段和证据边界见 [延迟拆分](latency.md)。这是一个样本的差异，尚不足以证明长期时延或分别归因每项改动。此计时从钩子开始，未量到发出 QQ 至钩子发现消息的等待，也没有手机显示回复的准确时间戳。

## 本开源版

为复用而做的改动包括去除具体机器路径和应用身份、本地配置初始化、数据目录参数、服务模板、Muse 接入文档、来源受限的只读取件口，以及可配置的 Muse 收件和回复脚本。运行环境的记忆文件、日志、状态和凭据不属于公开代码。

现场版本与通用化后的公开版本分别验收。现场收到回复证明该运行环境的链路可用；公开副本的代码合同由离线测试和 CI 核验，部署者还需完成自己的真实收发测试。

测试使用临时目录、虚构身份和本机临时端口。它们覆盖签名、白名单、队列、真实回执判定、失败码、未知结果不重发、重启后状态保留、显式绑定和 SDK 事件转换。不会连接腾讯，不会生成模型回复，也不会读取现用服务器的私有配置。
